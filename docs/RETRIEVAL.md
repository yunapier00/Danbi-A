# RAG 검색 품질 개선 (2026-10-10)

`search_knowledge` 도구의 검색을 측정 → 원인 분석 → 개선 → 검증 순서로 손봤다. 두 단계로 진행했다.
- **1단계 (1~5절): 검색 방식 개선.** 기존 Chroma DB(`chroma_db_dd3`)는 그대로 두고 검색 단계만 바꿨다.
- **2단계 (8절): 원본 문서로 DB를 새로 만듦.** `RAG_data/`의 원본 PDF·마크다운에서 새 DB(`chroma_db_v2`)를 만들어 서비스를 그쪽으로 바꿨다.

## 1. 측정 방법

- **검색 전용 평가:** LLM 없이 "정답 청크가 상위 몇 위에 오는가"만 채점한다 (`evals/retrieval_run.py`).
  - 정답 = 출처 + 조항·항목 제목(+ 본문 단어) 조건. 실제 DB 제목을 보고 정했고, `--check`로 모든 정답이 DB에 있는지 확인한다.
  - 지표:
    - hit@k: 정답이 상위 k개 안에 있는 비율
    - MRR: 첫 정답 순위의 역수 평균
    - 결과 글자 수: LLM 입력 크기, 즉 비용
- **두 세트로 나눴다:**
  - **조정용** `evals/retrieval.yaml` 44문항: 조항 표현 34 + 줄임말·구어체 10 ("학고", "조졸", "복전" …). 설정 탐색에 썼다.
  - **검증용** `evals/retrieval_holdout.yaml` 10문항: 탐색이 끝난 뒤 과적합 확인에만 썼다.
- 질문 임베딩은 한 번만 API로 계산해 `evals/results/embed_cache.json`에 저장한다. 이후 실험은 API 호출이 없다 (전체 실험 동안 약 60회 호출).

## 2. 원인 분석 (DB 청크 2,074개)

| 자료 | 청크 | 문제 |
|---|---|---|
| 강의시간표 안내자료 PDF | 1,088 (DB의 52%) | OCR이 깨진 조각, `[: 없음]`이 수십 번 반복되는 표, 표의 행마다 반복 저장된 같은 내용 |
| 학칙·시행세칙 | 755 | 조항 단위는 좋지만, 개정 이력(부칙)과 제목만 있는 청크가 섞여 있음 |
| 캠퍼스맵 | 104 | 한 건물의 위치·별칭·키워드가 따로 쪼개져 있음 (80자 미만 101개) |

기준선의 약점: 줄임말에 약하다("복전"은 정답을 못 찾음). 1위 정확도는 73%이고, 검색 한 번에 평균 3,552자가 LLM에 들어간다.

## 4. 최종 결과

| 세트 | 기준선 (k=8) | 개선 (k=6) |
|---|---|---|
| 조정용 44 | hit@1 73%, hit@3 95%, hit@k 98%, MRR 0.840, 3,552자 | hit@1 **86%**, hit@3 95%, hit@k **100%**, MRR **0.915**, **2,696자 (−24%)** |
| 검증용 10 | hit@1 90%, hit@3 100%, MRR 0.950, 3,070자 | hit@1 90%, hit@3 100%, MRR 0.950, **2,564자 (−16%)** |

- 검증 세트에서는 정확도가 같았다(떨어지지 않음). 기준선이 이미 90%일 만큼 쉬운 세트라 순위 개선 폭은 확인하지 못했다. 글자 수 감소만 확인됐다.
- 나빠진 질문도 있다:
  - "졸업하려면 몇 학점" 1위 → 3위
  - "1학점은 몇 시간" 1위 → 2위
  - "다전공 이수가 제한되는 단과대" 2위 → 6위: 같은 내용의 PDF 표 조각이 위를 차지한다. 상위 6개 안에는 든다.
- 좋아진 질문은 10개다. 줄임말 질문(학고·조졸·복전·자퇴), "범정관 어디"(위치 조각을 합침), "아파서 결석하면", "학점 포기" 등.
- 조정 세트를 보며 정한 값이라 실제 효과는 위 수치보다 작을 수 있다. 검증 세트를 늘리는 것이 다음 할 일이다.

## 5. 최종 구성 (`danbi/rag/retriever.py`, `RetrievalOptions` 기본값)

1. **질문 임베딩 확장:** `GLOSSARY`의 줄임말이 있으면 공식 용어를 덧붙여 임베딩한다. 예: `학고 맞으면 어떻게 돼? (학사경고)`.
2. **하이브리드:**
   - 벡터 상위 30과 키워드 상위 30을 RRF(k=60)로 합친다. 키워드 비중은 0.3이다.
   - 키워드 점수: idf × (제목 일치 3, 본문 일치 1).
   - 조사는 떼고, DB에 있는 가장 긴 앞부분으로 맞춘다 ('휴학은' → '휴학').
   - 청크 2,074개는 시작할 때 메모리에 올리므로 키워드 검색에는 DB 쓰기나 API가 필요 없다.
3. **조항 번호 정확 일치는 맨 앞:** "제29조"가 제목에 정확히 맞는 청크.
4. **잡음 뒤로:** 제목만 있는 청크, 제목 없는 PDF 조각 중 한글 단어 비율이 낮은 것(OCR 잡음), 부칙(질문에 부칙·경과·시행일이 없을 때).
5. **같은 제목은 최대 2개.**
6. **조각 합치기:** 같은 (출처, 대제목, 중제목)의 짧은(200자 미만) 조각을 합친다. 최대 8조각, 800자. 캠퍼스맵의 위치·별칭·키워드가 한 덩어리가 된다.
7. **표 정리:** `[: 없음]` 빈 칸을 지운다.

기준선 동작은 `RetrievalOptions.baseline()`으로 언제든 다시 잴 수 있다.

## 8. 2단계: 원본 문서로 DB 새로 만들기 (`scripts/build_rag.py` → `chroma_db_v2`)

### 왜

기존 DB는 만든 과정을 알 수 없고(읽기 전용), 품질 문제가 원본 처리 단계에서 생겼다.
- **학칙이 옛 버전이었다:** 기존 DB는 2026.05.07 개정본이고, `RAG_data/`에 있는 PDF는 **2026.08.31 개정본**이다.
  기존 DB의 "입대휴학 기간" 조항(학칙 제23조)은 2025.5.28.에 이미 삭제된 조항의 제목만 남은 것이었다.
- **잡음:** 개정 이력 표시(`<개정 1981.6.10., …>`), 화면 캡처 페이지의 OCR 잡음, `[: 없음]`이 반복되는 표, 표의 행마다 반복 저장된 같은 내용.

### 어떻게 (청크 2,074 → 1,210)

| 자료 | 처리 |
|---|---|
| 학칙·시행세칙 PDF (텍스트 PDF, pdfminer) | 조(條) 하나 = 청크 하나 (긴 조항은 항 단위로 나눔). 페이지 머리말과 개정 이력 표시를 지운다. 끊긴 줄은 원래 줄 끝의 공백 유무로 단어 사이인지 단어 중간인지 판단해 잇는다. 삭제된 조항(`[본조삭제]`)은 뺀다. 부칙은 날짜별로 하나로 묶는다. |
| 종합강의시간표 안내자료 PDF (표 많음, pdfplumber) | 페이지 위 머리말에서 섹션 경로(`Ⅲ. 주요 학사 관련 안내 > 3. 전공신청`)를 읽는다 (원문의 `3,`·`3 ` 같은 표기 오타도 처리). '가.' 소항목 단위로 나눈다. 표는 행·열을 살린 마크다운 표로 바꾸고, 병합 셀을 채우고, 전부 빈 열은 뺀다. 길면 머리 행을 반복해 나눈다(700자). 글자가 거의 없는 화면 캡처 페이지는 건너뛴다. |
| 마크다운 (캠퍼스맵·학사일정·도서관·셔틀) | `##` 단위로 나눈다. 건물 하나, 일정 하나, 셔틀 시간대 묶음이 각각 한 청크가 된다. |

- 각 청크 앞에 위치(`학칙 > 제7장 교과이수 및 졸업 > 제29조(교과이수단위)`)를 붙여 임베딩한다. 저장되는 본문에는 붙이지 않는다.
- 임베딩은 기존과 같은 `gemini-embedding-001`, RETRIEVAL_DOCUMENT, 3072차원이다(질문 임베딩과 맞아야 한다). 실제 API 테스트에서 저장 벡터를 다시 계산해 코사인 0.999 이상을 확인했다.
- 임베딩은 내용 해시로 캐시한다(`data/rag_build/embed_cache.jsonl`). 다시 만들 때는 바뀐 청크만 API를 부른다.

### 결과 (같은 검색 방식으로 두 DB 비교)

| | 조정용 44: hit@1 / hit@3 / hit@k / MRR / 글자 | 검증용 10: hit@1 / MRR / 글자 |
|---|---|---|
| 기존 DB · 기준선 k=8 | 75% / 98% / 98% / 0.860 / 3,552 | 90% / 0.950 / 3,070 |
| 기존 DB · 개선 검색 k=6 | **91%** / 98% / 100% / **0.948** / 2,696 | 90% / 0.950 / 2,564 |
| 새 DB · 기준선 k=8 | 82% / 95% / 98% / 0.883 / 3,482 | 90% / 0.950 / 2,898 |
| **새 DB · 개선 검색 k=6 (현재)** | 89% / **100%** / 100% / 0.936 / **2,631** | 90% / 0.950 / **2,471** |

- **검색 점수는 두 DB가 사실상 같다** (44문항 중 1문항 차이).
- 그래도 새 DB로 바꾼 이유는 점수에 안 잡히는 내용 품질이다:
  - **최신 규정:** 2026.08.31 학칙, 삭제 조항 정리.
  - **깨끗한 본문:** 개정 이력·OCR 잡음 없음, 표 구조 보존. LLM이 읽는 근거의 정확도가 좋아진다.
  - **다시 만들 수 있다:** 규정이 개정되면 PDF만 바꾸고 스크립트를 다시 돌린다.
- 새 DB만 쓴 기준선(k=8)도 기존 기준선보다 hit@1이 7%p 높다. 원본 정리만으로도 효과가 있었다.

### 과정에서 배운 것

- **처음 만든 새 DB는 기존보다 나빴다** (hit@1 84%, 글자 3,489).
  - 안내자료 청크가 평균 900자로 컸다 → 700자로 줄였다.
  - 연도별 이수기준표처럼 소제목만 다른 비슷한 표가 결과를 독점했다 → 같은 섹션(대·중제목)은 최대 2개로 바꿨다.
- **RRF는 한쪽 목록에서만 1위인 항목을 밀어낼 수 있다.**
  - 예: "다전공 이수가 제한되는 단과대"의 정답(시행세칙 제26조)은 벡터 1위였는데 최종 결과에서 빠졌다.
  - 대책: 벡터 상위 2개는 최종 결과에 반드시 남긴다 (`VECTOR_KEEP`). 조항 번호 일치 항목도 밀어내지 않는다.
  - 키워드 추출도 개선했다. 동사 어미를 뗀다 ('제한되는' → '제한').
- **정답 기준을 넓힌 문항이 3개 있다** (두 DB에 똑같이 적용):
  - 입대휴학: 학칙 제23조가 삭제돼 시행세칙 제15조 ②를 추가했다.
  - "복학 신청은 언제": 학사일정의 신청 기간을 추가했다.
  - "졸업하려면 몇 학점": 이수기준표의 졸업요구학점을 추가했다.
  - 모두 질문에 실제로 답하는 근거라서 넓혔지만, 결과를 본 뒤에 바꾼 것이라는 점은 밝혀 둔다.

### `RAG_data/other/`를 넣지 않은 이유

- **나무위키 사본 15개:** 누구나 고칠 수 있는 비공식 자료라 학교 공식 안내로 답하기에 부적합하다(사건사고·동아리 등 출처 신뢰도 문제). 또 CC BY-NC-SA 라이선스라 출처 표시와 같은 조건 공유 의무가 있다. 페이지 메뉴 같은 잡음도 많다.
- **2026학년도 수시·정시 모집요강:** 사용자는 학교 계정으로 로그인한 재학생이다. 이미 끝난 입시 연도라 지금(2027학년도 입시 기간) 섞이면 틀린 일정·조건을 안내할 위험이 있다.
- **학과정보 엑셀 변환본:** 공식 사이트에서 모은 `config/dept_list.yaml`과 학과 소스가 이미 있고, 폐과·옛 조직(SW융합대학)이 섞여 있다.
